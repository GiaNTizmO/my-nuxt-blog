4 ноября я гонял RAGE HW Bench на настоящей Wii U. Обычный цикл записывал 8 МиБ со скоростью примерно 165 МБ/с. Во втором цикле перед записью восьми слов я ещё и обнулял место под них. Казалось бы, работы прибавилось. А скорость выросла примерно до 1017 МБ/с. Тогда игра этим приёмом ещё не пользовалась. С этого замера и началась моя версия memset для Espresso.

**Что показал RAGE HW Bench.** В бенче я закрепил поток за ядром № 2 процессора Espresso и прогнал два цикла. Первый просто писал 32-битные слова подряд. Второй перед записью каждой следующей строки кэша выполнял инструкцию PowerPC `dcbz`, а потом тоже записывал восемь слов. В обоих случаях данные вычислялись в цикле. Это важно: в логе есть честное сравнение двух способов записи, но нет отдельного замера вызовов `memset(p, 0, n)` и `memset(p, 0xA5, n)`.

Вот повторный аппаратный замер от 12 ноября. Обе пары на одной шкале; чем длиннее полоса, тем быстрее запись. Размер буфера — в двоичных единицах, скорость — в миллионах байт в секунду.

~~~text
                     Скорость записи на Wii U, МБ/с
  8 МиБ   обычная    ██                       164,4
          с dcbz     ██████████             1 016,8

128 КиБ   обычная    ██████████████████     1 807,9
          с dcbz     █████████████          1 275,5
~~~

На 8 МиБ я получил **6,18×**. На 128 КиБ выиграл обычный цикл: **1,42×** относительно варианта с `dcbz`. Увидеть только верхнюю пару — и уже хочется положить новую инструкцию в каждую заливку. Хорошо, что в логе была нижняя.

Почему такие размеры? На этом ядре 512 КиБ кэша L2: маленький буфер туда помещается целиком, большой — нет. Адреса в бенче выровнены на 64 байта. Перед замером каждый цикл проходит буфер один раз для прогрева. Затем большой буфер проходится 4 раза, маленький — 256: в измеряемой части получается одинаковый объём записи, 32 МиБ. Кэш между проходами я принудительно не сбрасывал. Так что слово «холодный» здесь означает длинный проход за пределами L2, а не обещание, что перед каждым обращением кэш пуст.

**Откуда берутся лишние чтения.** У Espresso строка кэша — 32 байта. Если при обычной записи нужной строки в кэше ещё нет, процессор обычно сначала подтягивает её из памяти. Для записи одного байта это разумно: остальные 31 нужно сохранить. Но если я собираюсь переписать все 32, процессор только что сходил в память за данными, которые тут же выбросит.

`dcbz` (*data cache block zero*) позволяет сразу получить заполненную нулями строку, не читая её старое содержимое. Для `memset(p, 0, n)` целая строка на этом готова. Для заливки `0xA5` я следом пишу восемь слов `0xA5A5A5A5`. Зачем сначала нули, если нужны не нули? Чтобы не ждать чтения старых байтов. На маленьком прогретом буфере этого ожидания часто уже нет, а инструкция никуда не делась. И ещё деталь: нули пока находятся в кэше CPU. Если буфер потом читает GX2, видимость данных для GPU по-прежнему нужно обеспечивать отдельно.

**Что в итоге оказалось в порте.** Базовый вариант по образцу newlib уже умел писать словами: несколько байтов до выравнивания, затем четыре 32-битных слова за итерацию, остаток — отдельно. В сборке 327 я сохранил этот путь для запросов **меньше 128 байт**. Начиная со 128 байт перед заливкой целых строк код доходит до границы 32 байт обычными записями. Хвост меньше строки тоже пишет обычным способом. 128 байт — порог в коде порта; это совсем не те 128 **КиБ** из бенча, и по двум размерам буфера идеальный порог не подобрать.

Вот код из моего платформенного файла cafe_memops.cpp. Восемь присваиваний внутри цикла хорошо показывают, чем заливка произвольным байтом отличается от заливки нулями.

~~~cpp
inline void Dcbz(void* p) { __asm__ volatile("dcbz 0,%0" : : "r"(p) : "memory"); }

CAFE_MEMOPS_NOPATTERN void* FastMemset(void* dst, int c, size_t n)
{
    if (n < 128) return SlowMemset(dst, c, n);
    unsigned char* p = static_cast<unsigned char*>(dst);
    const unsigned char v = static_cast<unsigned char>(c);
    while (uintptr_t(p) & 31) { *p++ = v; --n; }
    const uint32_t w = v * 0x01010101u;
    while (n >= 32) {
        Dcbz(p);
        if (w) {
            u32a* q = reinterpret_cast<u32a*>(p);
            q[0] = w; q[1] = w; q[2] = w; q[3] = w; q[4] = w; q[5] = w; q[6] = w; q[7] = w;
        }
        p += 32; n -= 32;
    }
    while (n--) *p++ = v;
    return dst;
}
~~~

Тип u32a позволяет GCC записывать данные 32-битными словами с учётом правил алиасинга. А макрос перед функцией запрещает компилятору превращать узнаваемый цикл заполнения в библиотечный вызов: здесь я как раз реализую саму memset. Для нулевой заливки условие внутри цикла ложно: после Dcbz писать больше нечего. Для ненулевой умножение байта на 0x01010101 размножает его во все четыре позиции слова.

Вот конкретный вызов. Я беру выровненный массив и закрашиваю 130 байт, начиная со смещения 5. Справа и слева оставляю по метке:

~~~cpp
alignas(32) unsigned char buf[160]{};
buf[4] = 0x11;
buf[135] = 0x22;
FastMemset(buf + 5, 0xA5, 130);

assert(buf[4] == 0x11 && buf[135] == 0x22);    // соседи не изменились
assert(buf[5] == 0xA5 && buf[134] == 0xA5);    // края заливки
~~~

| Какие байты | Что делает FastMemset |
|---|---|
| 5–31: первые 27 байт | Пишет по байту, пока адрес не станет кратным 32. |
| 32–127: три целые строки | На каждую выполняет dcbz, затем пишет восемь слов 0xA5A5A5A5. Для нулевой заливки хватило бы одной dcbz на строку. |
| 128–134: последние 7 байт | Дописывает хвост по байту. |

Если сразу вызвать Dcbz(buf + 5), обнулится строка, **содержащая** этот адрес, — байты 0–31. Метка 0x11 исчезнет. У обычного цикла такого требования нет: он записывает ровно те байты или слова, которые я ему указал. А у версии с dcbz выигрыш появляется там, где я могу перезаписать строку целиком и можно сэкономить чтение из памяти. Даже тогда имеет значение состояние кэша — как показала нижняя пара полос на графике.

Ещё одно ограничение: этот путь рассчитан на обычную кэшируемую память с обратной записью. Для регистров устройств он не подходит. Если после CPU буфер читает GX2, о видимости новых данных для GPU по-прежнему заботится код передачи буфера.

**Как я проверял, что не затёр лишнего.** В старте игры проверка готовила два массива с одинаковым узором. В одном выполнялась быстрая заливка, в другом тот же диапазон заполнялся побайтно. Потом сравнивался **весь массив**, вместе с байтами до и после запроса. Перебирались смещения от 0 до 31 и размеры по обе стороны границ: 31/32/33, 127/128/129, а ещё нулевая длина. Значения — ноль и `0xA5`: второй случай заодно ловит реализацию, которая зачем-то свела любую заливку к обнулению. В двух запусках сборки 327 в Cemu общий тест `memset` и `memcpy` сообщил **13 377 проверок, 0 расхождений**. Для разбора проблем оставался переключатель на обычные циклы.

Поэтому в порте остались оба пути. Крупную нулевую заливку можно выполнить одной инструкцией на полную строку. А для короткого запроса обычный цикл обходится без подготовки границ. Какой из вариантов быстрее на уже прогретых данных, хорошо видно по замеру на 128 КиБ.
