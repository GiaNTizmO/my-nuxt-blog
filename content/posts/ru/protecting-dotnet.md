## Интро

Сегодня мы с вами разберём ситуации с защитой ПО на архитектуре .NET.

На данный момент (2025.11.09) в экосистеме .NET остаётся прежняя проблема — сборку с IL можно декомпилировать до читаемого C# (с учётом некоторых ограничений).

С этой проблемой сталкиваются многие разработчики, которые выводят .NET-проект в публичную среду и имеют коммерческие отношения. Зачастую проблема затрагивает лицензирование ПО, иногда — защиту интеллектуальной собственности (кода) от просмотра и модификации.

Собственно, возникает вопрос: *раз .NET «дырявый» — как победить данную проблему?*

И тут вступают разные способы защиты ПО от вскрытия и модификации:

1. Обфускаторы кода
2. Кастомные сборки .NET (`dotnet publish` с модифицированной средой .NET)
3. Виртуализаторы кода (ВМ для IL-опкодов)
4. Компиляция IL в машинный код до запуска приложения с помощью .NET Native AOT или Unity IL2CPP

Давайте рассмотрим в теории, как работают данные процессы.

## 1. Обфускация кода

Это процесс, который перед компиляцией (или сразу после неё) редактирует проект: меняет названия переменных, их положение в коде, добавляет «мусорный» и бессмысленный код, а также специальный код и атрибуты, которые мешают программам дизассемблирования.

**Пример обфускации кода**

До:

```csharp
public bool CheckLicense(string key)
{
    return key.Length == 16 && key.StartsWith("GM-");
}
```

После (упрощённый пример переименования и запутывания потока управления):

```csharp
public bool m0(string s0)
{
    int state = 0x5A2;
    while (true)
    {
        switch (state ^ 0x5A3)
        {
            case 1:
                if (s0.Length != (0x1F >> 1) + 1)
                    return false;
                state = 0x5A1;
                break;
            case 2:
                return s0.StartsWith("GM-");
            default:
                throw new System.InvalidOperationException();
        }
    }
}
```

А теперь рассмотрим плюсы данного решения:

1. **Можно внедрять постепенно** — начать с переименования внутренних типов и методов, а затем включать другие преобразования по мере проверки сборки.
2. **Простота использования** — не нужно глубоких знаний: подключил и используй.

Ну и к минусам:

1. **Нестойкая защита** — обфускация лишь усложняет реверс-инжиниринг. Если использовать публичный обфускатор, высок шанс, что его можно деобфусцировать, например, популярной утилитой `de4dot` и её многочисленными форками, которые комьюнити адаптирует под определённые сценарии.
2. **Нужно тестировать релизную сборку** — код, который ищет типы и свойства по имени через рефлексию, может сломаться после переименования. Отдельно стоит проверить сериализацию и загрузку плагинов.

| Плюсы | Минусы |
| --- | --- |
| Можно внедрять постепенно | Нестойкая защита |
| Простота использования | Нужны проверки релизной сборки |

## 2. Кастомная сборка .NET

Когда приложение публикуется в режиме `self-contained`, нужная версия .NET едет вместе с ним. Устанавливать рантайм на машину пользователя отдельно не нужно. Сам по себе этот режим использует штатный рантайм и может поставлять сборки приложения с обычным IL. [Документация по публикации .NET](https://learn.microsoft.com/dotnet/core/deploying/)

Кастомная сборка начинается там, где вы меняете сам рантайм. Например, можно изменить формат, в котором собственный загрузчик получает часть кода. Тогда приложение зависит от конкретного рантайма, который придётся выпускать вместе с ним. Для выполнения кода среде всё равно нужно получить его в понятном ей представлении.

Главная цена здесь — сопровождение. С обновлением .NET придётся переносить свои изменения, пересобирать рантайм под каждую поддерживаемую платформу и прогонять тесты на готовом пакете. Исправление безопасности в установленном на машине .NET само по себе не обновит копию, которая поставляется с приложением. [Сборка CoreCLR из исходников](https://github.com/dotnet/runtime/blob/main/docs/workflow/building/coreclr/README.md)

## 3. Виртуализация кода

Берём один метод, переводим его логику в команды для собственного интерпретатора и поставляем этот интерпретатор вместе с программой. IL метода теперь в основном вызывает интерпретатор, а сама логика представлена последовательностью его команд.

Представим метод `return x + 1`. Простая стековая ВМ сначала кладёт на стек `x` и `1`, затем складывает два верхних значения и возвращает результат. В реальном методе к этому добавятся ветвления, вызовы и работа с исключениями. Под каждую такую конструкцию нужно определить поведение и проверить, что оно совпадает с исходным методом.

При анализе виртуализированного метода сначала нужно разобраться, что означают команды интерпретатора. За этот дополнительный слой платит и разработчик. Дополнительная работа интерпретатора особенно заметна в горячих циклах, а отладка изменённого метода сложнее. Начните с нескольких компактных методов, замерьте время выполнения и проверьте пограничные случаи на той сборке, которую получит пользователь.

## 4. Компиляция в машинный код

**Native AOT** компилирует IL в машинный код при публикации. Приложение собирается под конкретную платформу, например Windows x64 или Linux Arm64, и выполняется без JIT. Для сравнения, **ReadyToRun** добавляет скомпилированный код в сборки, которые по-прежнему содержат IL. [Native AOT](https://learn.microsoft.com/dotnet/core/deploying/native-aot/) · [ReadyToRun](https://learn.microsoft.com/dotnet/core/deploying/ready-to-run)

Что это даёт с точки зрения защиты? Метод, скомпилированный Native AOT, приходится разбирать как машинный код. Алгоритм при этом всё так же выполняется на машине пользователя. При сборке анализатор должен определить, какой код и метаданные понадобятся во время выполнения. Рефлексию стоит проверить на опубликованной сборке, а генерацию кода через `Reflection.Emit` придётся заменить.

У Unity свой путь — **IL2CPP**. Он переводит IL в C++, после чего платформенный компилятор превращает этот C++ в машинный код. Это часть сборки Unity. У обычного проекта .NET соответствующий вариант публикации — Native AOT. [Документация Unity по IL2CPP](https://docs.unity3d.com/6000.0/Documentation/Manual/il2cpp-introduction.html)

## Что это значит для лицензирования

Вернёмся к `CheckLicense` из начала статьи. Проверка длины и префикса показывает, как меняется форма метода после обфускации. В настоящей лицензии нужно проверить ещё и то, кто её выпустил. В офлайн-сценарии издатель подписывает данные лицензии закрытым ключом, а приложение проверяет подпись открытым ключом. Подписать стоит все поля, которые влияют на права пользователя, например срок действия и набор функций. [Проверка цифровой подписи в .NET](https://learn.microsoft.com/dotnet/api/system.security.cryptography.ecdsa.verifydata)

Подпись защищает данные лицензии от подделки, пока проверка в клиенте выполняется как задумано. Если платная функция обращается к вашему серверу, проверяйте право на операцию на самом сервере. Для приложения, которое целиком работает офлайн, выбирайте обфускацию, виртуализацию или AOT по тому, сколько сложности они добавят к анализу и сколько будут стоить при выпуске и сопровождении.
